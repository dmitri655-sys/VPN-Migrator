# VPS Migrator · MVP 0.2.0

Открытая CLI-утилита на Python для переноса **3x-ui/Xray** между Ubuntu/Debian VPS через SSH. Интерфейс и инструкции на русском. Лицензия MIT. Сторонних Python-зависимостей нет.

**Сначала показывается план.** Команда `migrate --apply` только создаёт staging. `commit --apply` размещает файлы, но не запускает службу. `activate --apply --accept-source-code` отдельно разрешает запуск перенесённого root-кода и его сетевых слушателей. Для каждой записи нужно повторить IP назначения в `--confirm`.

Старый VPS продолжает работать. Утилита не меняет DNS, адреса интерфейсов, маршруты, SSH, sysctl, UFW/nftables/iptables и не выключает старую службу. Автоматической смены IP на существующем сервере нет. Docker AWG2 не переносится.

## Что входит в перенос

| Объект | Действие |
|---|---|
| `/etc/x-ui/x-ui.db` | Online Backup API SQLite (`Connection.backup`, эквивалент `.backup`), включая WAL; затем `integrity_check` |
| `/etc/x-ui` | Остальные обычные файлы и каталоги; живые `x-ui.db-wal`, `-shm`, `-journal` не копируются |
| `/usr/local/x-ui` | Установка и бинарники без загрузки неизвестных install-скриптов |
| `/root/cert/sakha-ai.ru` | TLS; можно выбрать другой каталог через `--cert-dir /root/cert/DOMAIN` |
| `x-ui.service` | Unit из `/etc`, `/usr/lib` или `/lib/systemd/system`, устанавливается в `/etc/systemd/system` |
| `/etc/default/x-ui` | Переносится, если явно указан в unit; проверяется безопасный SQLite-поднабор переменных; участвует в rollback |

Сохраняются root:root и безопасные mode-биты, включая исполняемость бинарников. Для базы/конфигурации устанавливаются `0600`, каталогов `0700`; TLS-файлов `0600`, TLS-каталогов `0700`. Права на остальные файлы установки сохраняются. ACL, xattrs, capabilities, SELinux-контексты, не-root владельцы, symlinks/hardlinks как ссылки, устройства, сокеты, FIFO и special bits не поддерживаются. Hardlink исходного обычного файла сохраняется как независимый файл. Symlink в TLS, например на `/etc/letsencrypt`, приводит к отказу, а не копированию посторонних путей.

Unit должен запускать `/usr/local/x-ui/x-ui` единственным `ExecStart`, без аргументов, Exec-хуков и внешнего RootDirectory. Стандартный unit 3x-ui (`x-ui.service.debian`) поддерживается: из дополнительных строк допустимы только `ExecReload=/bin/kill -USR1 $MAINPID`, `Environment="XRAY_VMESS_AEAD_FORCED=false"` и `KillMode=mixed`. Единственный допустимый drop-in — `/etc/systemd/system/x-ui.service.d/10-xui-sandbox.conf`, который создают install.sh/update.sh 3x-ui. В нём разрешены только `ReadWritePaths`/`ReadWriteDirectories` со стандартными каталогами 3x-ui и `SystemCallFilter=@system-service` с `SystemCallErrorNumber=EPERM`. Такой drop-in переносится вместе с unit и участвует в rollback; при `SystemCallFilter` на цели нужен systemd 239+. Любые другие drop-ins и файлы в каталоге drop-in приводят к отказу. Допустим один `EnvironmentFile=/etc/default/x-ui` (также с необязательным `-`). В нём поддерживаются только `XUI_DB_TYPE=sqlite`, `XUI_DB_FOLDER=/etc/x-ui`, `XUI_BIN_FOLDER=/usr/local/x-ui/bin` и стандартный `XUI_LOG_LEVEL`. Неизвестные переменные, PostgreSQL, другие пути, прочие inline Environment и shell-подстановки приводят к отказу; значения в ошибках скрыты. Это намеренно ограниченный формат, не универсальный parser systemd env. Пользователь службы — root (явно или по умолчанию). Для остановки дочерних процессов требуются `KillMode=control-group` или `mixed` и `SendSIGKILL=yes` (явно или по умолчанию). Нестандартная установка требует отдельной адаптации.

После SQLite backup программа считает inbounds/users/settings и клиентов в JSON inbounds. Сводка без личных данных попадает в manifest и проверяется после передачи и перед commit. Непустая таблица `nodes` блокирует перенос: внешние узлы не поддерживаются. Счётчики берутся из снимка, а не повторно из меняющейся живой базы.

## Требования

* Управляющая машина — Linux с Python **3.9+** и OpenSSH client. Можно запускать с новой VPS, подключаясь к ней самой по её IP; SSH root-доступ должен работать также к источнику. Нативный Windows-контроллер не поддерживается; используйте Linux/WSL.
* Обе VPS: Ubuntu или Debian, root-доступ по SSH, Python 3.9+, systemd, `openssl`, `ss`, `ldd` и Python с модулем sqlite3. Ключи SSH предпочтительны; пароль вводится только в запросе OpenSSH, не в аргументах программы.
* Одинаковая архитектура CPU, glibc на цели не старее исходной. Это предварительная проверка, а не доказательство наличия всех библиотек стороннего бинарника. Проще выбрать ту же ОС и версию.
* **Чистая цель**: нет `/etc/x-ui`, `/usr/local/x-ui`, выбранного TLS-каталога, unit/drop-ins/ссылок автозапуска x-ui. Никакая существующая установка автоматически не заменяется.
* Staging `/var/lib` и конечные каталоги — на одной файловой системе. Свободно не менее трёх размеров установки + 256 MiB. Лимит содержимого архива — 8 GiB и 100000 записей. На управляющей машине нужен запас под полный архив.
* На время копирования не обновляйте 3x-ui/Xray, сертификаты и конфигурацию. SQLite может работать в WAL, исходная служба не останавливается. Изменения базы **после снимка** не попадут на цель: это не непрерывная репликация, счётчики и клиенты могут разойтись.

Подготовьте зависимости на обеих VPS через консоль провайдера или SSH:

```sh
sudo apt-get update
sudo apt-get install -y python3 openssl iproute2 libc-bin
```

На машине, с которой запускаете перенос:

```sh
sudo apt-get install -y python3 openssh-client unzip
```

Программа сама не устанавливает пакеты, не меняет firewall и не запускает сторонний установщик. На source/target не требуется pip или установка самой утилиты: worker передаётся в команду SSH и работает через Python standard library.

## Установка из архива — без pip

Скачайте `vps-migrator-0.2.0.zip` из приложенных артефактов. Загрузите его на управляющую Linux-машину, распакуйте и войдите в папку:

```sh
unzip vps-migrator-0.2.0.zip
cd vps-migrator
python3 -m vps_migrator --help
```

В примерах ниже команды выполняются из этой папки. Это полноценный способ запуска, не требующий программирования. `install.sh` — необязательное добавление команды, описано в конце.

Также приложен один готовый файл `vps-migrator-0.2.0.pyz`: загрузите его на Linux и запускайте `python3 vps-migrator-0.2.0.pyz --help`. Распаковка и pip не нужны; далее вместо `python3 -m vps_migrator` подставляйте `python3 /путь/vps-migrator-0.2.0.pyz`.

## 1. Проверить SSH host keys

После подготовки ключей можно выполнить `python3 -m vps_migrator wizard` (или `python3 vps-migrator-0.2.0.pyz wizard`). Мастер спросит IP, SSH-порты и TLS-каталог, покажет dry-run и отдельно запросит подтверждение для staging, commit и запуска. Пустой ответ останавливает процесс; для запуска дополнительно нужно слово `ЗАПУСТИТЬ`. UUID выводится после staging, продолжить можно обычными командами ниже. При нестандартном SSH-порте добавляйте `--port` к status/commit/activate/rollback.

Команды ниже остаются доступны для ручного управления и повторного входа после обрыва мастера.

Утилита всегда использует `StrictHostKeyChecking=yes`: неизвестный или изменённый ключ блокирует работу. Никогда не обходите ошибку через `StrictHostKeyChecking=no`.

На **консоли провайдера каждой VPS**, не через ещё не проверенное SSH-соединение, посмотрите отпечаток:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

На управляющей машине сделайте обычное первое подключение к каждому IP:

```sh
ssh -F /dev/null -o StrictHostKeyChecking=ask -o GlobalKnownHostsFile=/dev/null root@СТАРЫЙ_IP
ssh -F /dev/null -o StrictHostKeyChecking=ask -o GlobalKnownHostsFile=/dev/null root@НОВЫЙ_IP
```

Сравните SHA256-отпечаток с консолью провайдера, и только при совпадении ответьте `yes`. Выход — `exit`. Ключи попадут в `~/.ssh/known_hosts`. Если OpenSSH предлагает другой тип host key, сравните соответствующий `.pub` на сервере. Один `ssh-keyscan` без независимого сравнения не защищает от подмены.

SSH-порт не 22: добавьте `-p 2222` в первое подключение, затем используйте соответствующие `--source-port`/`--target-port` или `--port` в утилите.

## 2. Задать адреса и посмотреть план

Замените примеры IP реальными адресами. IPv4 и IPv6 принимаются без `root@` и без квадратных скобок. DNS-имена/SSH-алиасы не принимаются.

```sh
OLD=192.0.2.10
NEW=192.0.2.20
python3 -m vps_migrator discover "$OLD"
python3 -m vps_migrator migrate --source "$OLD" --target "$NEW"
```

Последняя команда — dry-run: чтение инвентаризации и preflight, без архивов, staging, остановки/запуска или изменения конфигурации серверов. Как у любого SSH-подключения, могут появляться системные записи о входе в журнале sshd.

Для отдельного SSH-ключа/known_hosts глобальные параметры идут **перед** командой:

```sh
python3 -m vps_migrator --identity ~/.ssh/id_ed25519 --known-hosts ~/.ssh/known_hosts migrate --source "$OLD" --target "$NEW"
```

Конфигурация `~/.ssh/config` намеренно не используется: нет неявных ProxyCommand/LocalCommand/туннелей. SSH-agent можно использовать, agent forwarding отключён. Ключи обоих серверов должны быть в known_hosts пользователя, под которым запускается утилита; при запуске через sudo это другой пользователь.

## 3. Подготовить staging

```sh
python3 -m vps_migrator migrate --source "$OLD" --target "$NEW" --apply --confirm "$NEW"
```

Программа покажет `Задание: UUID`. Сохраните его, например:

```sh
JOB=вставьте-UUID-из-вывода
python3 -m vps_migrator status "$NEW" "$JOB"
```

После успеха ожидается `state: staged`. Файлы находятся только под `/var/lib/vps-migrator/UUID/stage` на новой VPS. Исходный архив удаляется после попытки передачи; закрытая временная копия контроллера удаляется при штатном завершении. На цели архив остаётся для восстановления и аудита.

SHA-256 проверяется для архива и каждого файла. Пути, типы, владельцы, права и manifest проверяются до распаковки. TLS проверяется через OpenSSL: есть хотя бы одна действующая PEM-пара сертификат/ключ с одинаковым публичным ключом. Это **не** проверка SNI, полного chain, всех пар или доступности снаружи.

## 4. Разместить файлы, затем отдельно разрешить запуск

Можно сначала посмотреть состояние без записи:

```sh
python3 -m vps_migrator commit "$NEW" "$JOB"
python3 -m vps_migrator commit "$NEW" "$JOB" --apply --confirm "$NEW"
```

Ожидается `committed`: файлы размещены, выполнен `systemctl daemon-reload`, сервис ещё не запущен. Перед запуском проверьте конфигурацию на новой VPS: привязки к старому IP, абсолютные пути сертификатов, зависимости и доменные ссылки. Утилита их не переписывает. Проверка staged checksums сделана перед commit; если после commit вы вручную редактируете файлы, ответственность за эти изменения на вас.

Перенесённые бинарники и unit происходят с вашего старого сервера. Считайте источник доверенным: запуск разрешает исполнение его кода с правами root. Запуск Xray может также выполнять поведение, заданное исходной конфигурацией (например, сетевые функции WireGuard). Разрешайте запуск только после просмотра настроек.

```sh
python3 -m vps_migrator activate "$NEW" "$JOB" --apply --confirm "$NEW" --accept-source-code
python3 -m vps_migrator health "$NEW" "$JOB"
```

При ошибке запуска или локального health check программа остановит **новую** службу и откатит файлы обратно в staging. При жёстком прерывании нужен ручной `rollback` ниже. Исходная служба не затрагивается.

Автозапуск после перезагрузки утилита не включает. После успешной проверки клиентов при желании отдельно выполните **на новой VPS**:

```sh
sudo systemctl enable x-ui.service
```

Если потом нужен rollback, сначала отключите добавленный вами автозапуск `sudo systemctl disable x-ui.service` (на новой VPS). Собственные ссылки автозапуска утилита не создаёт и не удаляет.

## Проверки для вашего набора портов

| Назначение | Ожидаемый локальный сокет |
|---|---|
| Reality | 443/tcp |
| XHTTP | 8443/tcp |
| Hysteria | 443/udp |
| MTProto | 36282/tcp |
| WG3.1 | 46331/udp |
| Подписка | 2096/tcp |
| Панель | 58291/tcp |

Перед переносом/commit эти порты на цели должны быть свободны. После запуска **все** ожидаются в выводе `ss`, а `x-ui.service` должен быть active. Набор портов фиксирован для этого MVP; для другой установки измените `PORTS` в `remote.py` осознанно. Сокеты проверяются локально без атрибуции PID: это не полная проверка работоспособности протоколов.

Если Hysteria, MTProto или WG3.1 запускаются отдельными systemd/Docker-службами вне x-ui, эти службы **не перенесутся**. Health check обнаружит отсутствующие порты и откатит запуск. Наличие порта на исходной VPS не означает, что им управляет x-ui. AWG2 намеренно вне MVP, даже если работает на том же сервере.

Проверьте с внешнего устройства:

1. SSH на новую VPS и HTTPS панели с правильным SNI/доменом.
2. Подписку и ссылки: там может остаться старый IP или домен.
3. Подключение отдельным тестовым клиентом для каждого протокола, включая UDP.
4. Firewall ОС и правила/группы безопасности провайдера. Утилита не открывает порты.
5. Срок действия TLS и корректный chain. Копирование сертификата не переносит ACME-аккаунт, cron продления, nginx/caddy или `/root/.acme.sh`.

DNS, клиентские ссылки и переключение трафика меняйте самостоятельно, отдельным решением после проверок. Если домен остался тем же, клиент без проверки DNS может продолжать ходить на старую VPS. На двух работающих серверах учёт трафика/лимиты могут расходиться.

## Откат и сбой соединения

```sh
python3 -m vps_migrator status "$NEW" "$JOB"
python3 -m vps_migrator rollback "$NEW" "$JOB"
python3 -m vps_migrator rollback "$NEW" "$JOB" --apply --confirm "$NEW"
```

Откат останавливает установленную новую службу, перемещает её корни обратно в staging и перечитывает systemd. Новые записи базы сохраняются в этом staging, а не удаляются. Старый сервер остаётся доступен. После отката `state: rolled-back`. Это не обратная синхронизация клиентов/трафика со старым сервером.

Журнал намерений пишется атомарно с fsync **перед** каждым перемещением; перемещения выполняются на одной файловой системе. Если видите `committing`, `activating`, `rolling-back` после обрыва — выполните rollback; при занятой блокировке дождитесь завершения оставшегося удалённого worker. Повторный commit/activate для завершённого состояния не выполняется. После rollback сделайте новый migrate с новым UUID.

После проверенного отката можно удалить именно резервные данные задания (необратимо):

```sh
python3 -m vps_migrator discard "$NEW" "$JOB"
python3 -m vps_migrator discard "$NEW" "$JOB" --apply --confirm "$NEW"
```

`discard` разрешён только для `staged`, `rolled-back` или неполной подготовки без state.json. Для `active`, `committed`, `committing`, `activating`, `rolling-back` он запрещён. Если оборвался export, аналогично проверьте `status "$OLD" "$JOB"` и используйте discard для этого UUID на источнике. Для partial staging status покажет `incomplete-staging-or-export`. На активной цели архив остаётся: автоматической очистки резервов нет.

Если worker ещё работает, следующая команда получит ошибку блокировки. Не удаляйте lock вручную: блокировка привязана к процессу и снимается после его выхода. Если обнаружен конфликт rollback («оба пути существуют»), ничего не перезаписывается — требуется ручная проверка через консоль. Программа не пытается угадывать, какие из чужих файлов удалить.

Вновь созданные пустые родительские каталоги (например `/root/cert`) после rollback могут остаться. Гарантия — возврат четырёх переносимых корней и env-файла, если он переносился, и остановка новой службы, а не побитовое восстановление всей ОС. Журнал/архив на цели сохраняется. Обрыв питания и внешние изменения файлов требуют проверки состояния; это не распределённая транзакция между VPS.

## Безопасность резервных копий

В архиве есть приватные TLS/Reality-ключи, SQLite с учётными данными, токены и клиенты. SSH шифрует передачу; архив на диске **не зашифрован**. Рабочий каталог имеет `0700`, файлы — закрытые права. Защитите диск/снапшоты управляющей машины и обеих VPS. Не загружайте payload/manifest/state в Git и не публикуйте вывод инвентаризации без удаления IP/machine-id.

Root-пароль не принимается ни как CLI-аргумент, ни как файл/переменная: его спрашивает только OpenSSH через терминал; root-пароль недоступен Python. Без терминала используйте заранее подготовленный SSH-ключ. Приватный SSH-ключ утилита не читает. Повторные подключения с паролем могут давать несколько запросов.

SHA-256 обнаруживает повреждение при передаче/изменение staging, но не доказывает безопасность скомпрометированного источника. Утилита не является антивирусом и не делает hardening VPS. Установка Linux-пакетов, секреты, инфраструктура провайдера, внешние файлы и отдельные сервисы остаются вашей ответственностью.


Установщик создаёт ссылку в `~/.local/bin` на launcher внутри проекта; pip, venv и загрузка зависимостей не нужны. Существующую команду он не перезаписывает. Не перемещайте папку после установки. Без установки используйте `python3 -m vps_migrator` или готовый `.pyz`.

## Разработка и тесты

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q vps_migrator tests
```

Тесты используют изолированные временные каталоги и mock systemd/SSH: они не мигрируют ваш сервер. Проверяются WAL-снимок, архивы с traversal/links/devices/duplicates, checksums, host key policy, dry-run, подтверждение, прерванный commit и rollback. Дополнительные тесты проверяют preflight и состояния. Linux CI описан в `.github/workflows/tests.yml`; наличие workflow не означает, что CI уже прошёл.

См. [TESTING.md](TESTING.md) для ручной проверки на двух одноразовых VPS и [VALIDATION.md](VALIDATION.md) для фактического отчёта. Проверены Windows-тесты ядра и тесты на Ubuntu WSL, включая синтетический цикл export → stage → commit → rollback с настоящими Linux-правами, SQLite WAL, OpenSSL и файловыми блокировками. В этом цикле команды systemctl и факты VPS подменены. Настоящий перенос по SSH и запуск Xray между двумя VPS ещё не проверены. Доступа к вашим VPS не было, никаких подключений к ним не выполнялось.

Основа реализации: [SQLite Online Backup API](https://www.sqlite.org/backup.html), [OpenSSH StrictHostKeyChecking](https://man.openbsd.org/ssh_config), [Python tarfile](https://docs.python.org/3/library/tarfile.html). Извлечение здесь выполняется вручную по разрешённым путям без `extractall`.
