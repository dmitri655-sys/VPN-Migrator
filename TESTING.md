# Проверка перед использованием с реальными данными

## Что уже проверяет автоматический набор

`python3 -m unittest discover -s tests -v` выполняет тесты ядра в временных каталогах, без root-операций над ОС и без исходящих SSH. Тест WAL держит исходное соединение открытым, записывает данные в WAL, делает backup, затем проверяет независимость снимка от следующих записей. Тесты транзакций подменяют root-каталог и команды systemd; один тест выбрасывает исключение на втором rename, другой моделирует остановку процесса до/после rename. `activate` с неуспешным health должен вернуться в rolled-back.

Тесты Windows могут проверить Python-логику и SQLite, но chmod/chown/flock/symlink/systemd и SSH нужно проверять на Linux. CI-файл рассчитан на Ubuntu 22.04/24.04 и Debian 12/13, контейнерный CI не запускает настоящий systemd. Валидация TLS через OpenSSL покрывается тестом с настоящими временными ключами там, где OpenSSL доступен; это не сетевой TLS handshake.

На Linux с root-доступом можно отдельно выполнить:

```sh
sudo python3 tools/integration_smoke.py
```

Smoke создаёт две синтетические установки в новых `/tmp`-каталогах. Проверяет настоящий WAL snapshot при открытой исходной базе, архив, OpenSSL, передачу через поток, staging, commit, root:root/0600, flock и rollback с сохранением новых данных. `/etc` и `/usr/local` настоящей ОС не затрагиваются: все пути перенаправлены внутрь `/tmp`. Команды systemctl и сведения о VPS подменяются; Xray не выполняется, SSH не используется. Если запускаете из WSL, сначала скопируйте проект с `/mnt/c` на Linux-файловую систему: права DrvFS могут отличаться от ext4.

В 0.2 добавлены проверки стандартного EnvironmentFile и его отката, aggregate counts из снимка, отказа при nodes/повреждённом client JSON, а также отказов/EOF на этапах мастера. При переносе env-файла ручная проверка rollback должна охватывать также `/etc/default/x-ui`. Для свежей установки 3x-ui проверяйте и drop-in `/etc/systemd/system/x-ui.service.d/10-xui-sandbox.conf`: после commit он на месте, после rollback — снова в staging; `systemctl cat x-ui` на цели показывает его.

## Протокол проверки на двух одноразовых VPS

Используйте отдельные VPS без рабочих клиентов и ключей. Не публикуйте выданный программой архив. Настройте тестовую 3x-ui на источнике по документации выбранной версии, с семью ожидаемыми портами, настоящей тестовой PEM-парой в `/root/cert/sakha-ai.ru`. Источник и цель должны удовлетворять ограничениям README. Убедитесь, что каждый слушатель действительно запускается x-ui, иначе автоматический запуск ожидаемо откатится.

1. Сделайте snapshots обеих тестовых VPS средствами провайдера. Запишите `systemctl is-active x-ui` и `ss -lntu` на источнике, hashes тестовых файлов конфигурации. Не делайте сырое сравнение SQLite при работающем WAL.
2. Получите host key fingerprints через консоль провайдера. Проверьте обычные SSH-входы и `known_hosts` управляющей машины.
3. Выполните dry-run. Убедитесь, что на VPS не появился `/var/lib/vps-migrator`, а исходная служба active. Системные SSH-журналы входов допустимы.
4. Повторите с намеренно неизвестным host key в отдельном known_hosts: должно быть отказано до запуска worker. Повторите с изменённым ключом: тоже отказ. Не отключайте проверку.
5. Создайте на цели `/etc/x-ui/marker`. Preflight должен отказать и сохранить marker. Удалите только собственный тестовый marker/каталог вручную, верните цель в чистое состояние.
6. Займите на цели 8443/tcp тестовым процессом. Preflight должен отказать. Освободите порт.
7. Запустите migrate --apply с подтверждением. Проверьте staged, `stat` прав TLS/DB (root:root 0600, каталоги 0700), hashes и `PRAGMA integrity_check` снимка. На цели x-ui отсутствует в active; источник продолжает работать.
8. Commit без --apply должен показать dry-run. Commit с неверным --confirm должен отказать без размещения файлов. Правильный commit переводит в committed, но не запускает службу.
9. Activate без --accept-source-code должен отказать. Полный activate должен дать active и все ожидаемые сокеты. Проверьте внешними клиентами каждый протокол/панель/подписку и SNI. Сеть/провайдер могут блокировать доступ, даже когда локальный health успешен.
10. Rollback должен остановить новую службу, вернуть все четыре корня в staging, сохранить новые записи БД. Старый сервер должен быть active. Ссылок автозапуска от утилиты быть не должно.
11. На свежей цели повторите перенос; между commit и activate сломайте тестовую конфигурацию так, чтобы запуск x-ui не прошёл. Activate должен вернуть ошибку и rolled-back. Не используйте рабочие конфигурации для этого теста.
12. На очередной свежей цели имитируйте обрыв управляющего SSH во время передачи: источник остаётся active; частичное задание цели можно найти по UUID, посмотреть status и discard. Не удаляйте рабочие данные/lock вручную.
13. Проверка жёсткого падения commit: в одноразовой среде остановите remote worker между перемещениями файлов. После его выхода статус committing, повторный rollback восстанавливает staging. Не применяйте такой fault injection к рабочей VPS.

Сохраните версии ОС/Python/OpenSSH/3x-ui/Xray, команды, exit codes и обезличенный результат. Не прикладывайте БД, ключи или полный журнал приложения к публичным issue. Эта ручная матрица в текущей среде не выполнялась: проверка на реальных VPS остаётся обязательной перед рабочим переносом.
